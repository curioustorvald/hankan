# Provenance

This file records which source supports each subsystem, so that an auditor
can check that the project is a clean-room implementation. The rules it is
held to are in `CLAUDE.md` (“Provenance”). It is maintained alongside the
code: every subsystem that encodes knowledge of the file formats gets a row
under “Subsystems”, with the clauses it relies on.

### Corpus

`provenance/Corpus/` holds public forms used only as an input/output
compatibility and regression corpus: 2,464 HWP 5.0 files, 260 HWPX files and
7 HWP 3.0 files. They were collected by the scripts in `tools/corpus/` from
the public sources listed in `README.md`. Reference renders (JPEG) are made
on a separate Windows machine with a viewer and copied over; only `.hwp`,
`.hwpx` and `.jpeg` files cross between the two machines. The development
machine (Linux) has no Hancom software installed.

## Derived material

`provenance/derived/` holds machine-readable transcripts of the six sources
(Markdown, JSON, page renders, and the XSD annexes of KS X 6101 as `.xsd`
files), generated by `python3 tools/spec/build.py`. They add no information
beyond the sources; `provenance/derived/SOURCES.json` ties each one to the
SHA-256 of its original. They are git-ignored and never distributed, because
the ᄒᆞᆫ글 documents may only be redistributed unmodified and KS X 6101 is
copyrighted.

### General-purpose specifications

The engine also implements general-purpose formats that are not specific to
ᄒᆞᆫ글 documents. They were written from the public specifications below
(“documentation for unrelated technologies”, `CLAUDE.md`), not from any
ᄒᆞᆫ글-related source, and without third-party code: the engine has no
dependencies.

| id | specification | used for |
|---|---|---|
| `ms-cfb` | Microsoft, *[MS-CFB]: Compound File Binary File Format* | the container of `.hwp` files |
| `zip` | PKWARE, *APPNOTE.TXT – .ZIP File Format Specification* | the container of `.hwpx` files |
| `rfc1951` | RFC 1951, *DEFLATE Compressed Data Format* | compressed streams and ZIP entries |
| `crc32` | CRC-32 as defined for ZIP (IEEE 802.3 polynomial) | ZIP entries; see C1 |
| `xml` | W3C, *Extensible Markup Language (XML) 1.0* | reading and editing OWPML XML |
| `rfc4180` | RFC 4180, *Common Format for CSV Files* | the user's data |
| `encoding` | WHATWG *Encoding Standard* (`utf-8`, `euc-kr`) | decoding the user's data |

## Corpus observations

Where the sources are silent, ambiguous or (in two places) differ from the
files that exist, the engine follows what the corpus shows. Each such point
is listed here. Each is checked over the whole corpus by
`node tools/check/corpus.js` (the C-numbered checks); none was taken from
any other source.

| id | observation | sources say | checked |
|---|---|---|---|
| C1 | Every compressed record stream is a raw DEFLATE stream followed by 8 bytes: the CRC-32 and the length of the uncompressed data. | hwp5 §1 p.5: compressed with zlib; the layout of the compressed data is not described. | all 2,504 compressed BodyText streams (and every DocInfo) |
| C2 | In the parameter set of a field's CTRL_DATA (which holds the field name), the item id takes 4 bytes. | hwp5 표 51 p.31: WORD id, WORD type. With a WORD id no field's item has a valid type. The CTRL_DATA of other controls (section definitions, tables) fits neither reading; the engine never reads it. | all 48 field CTRL_DATA records |
| C3 | The paragraph control mask is the OR of `1 << code` over the control characters in the text, the paragraph end (13) not included. | hwp5 표 58: “(UINT32)(1<<ctrlch) 조합”; whether 13 counts is not stated. | 250,382 paragraphs |
| C4 | The paragraphs of a list (table cell, header, footnote, text box) are records at the same level as their LIST_HEADER, following it. | hwp5 p.11: paragraphs are serialised after the list header; levels not stated. | 155,184 lists |
| C5 | In a table cell's LIST_HEADER the cell properties of 표 80 begin at byte 8; the cell addresses read there tile every table exactly. | hwp5 표 65 p.36 gives a 6-byte list header; 표 79 p.40 puts the cell properties after it. | 7,152 tables |
| C6 | An extended control character carries its control id in code units 1–2; fields of unknown type have `%unk` in the record but the specific id in the text. | hwp5 p.12 calls this part a “pointer”. Informational: the engine pairs controls with characters by order, as hwp5 p.11–12 describe. | 15,502 controls |
| C7 | The `textpos` of an OWPML `<lineseg>` counts positions like HWP 5.0 (a control counts 8). `<linesegarray>`/`<lineseg>` occur in every corpus paragraph but are not in the standard's schema. | not in owpml-ksx6101 | 26,612 paragraphs |
| C11 | A form-object record (HWPTAG_FORM_OBJECT) is: a 4-byte ASCII type tag (“tbc+” check box, “tbr+” radio button) written twice, the length n of a text as UINT32 and again as WORD, then n UTF-16 units of property text, “Name:type:value” items separated by spaces, in the syntax of the field command shown in owpml-ksx6101 §10.7.3.1, with the attribute names of owpml-ksx6101 §10.11. The check state is the item “Value:int:N”. **How this was derived:** the 103 form-object records of the 8 corpus documents that have any were displayed as hex and text (all are check boxes or radio buttons, all unchecked); the framing above holds for all of them, and the text parses completely in the documented syntax. N = 1 for “checked” is read from the order of OWPML's UNCHECKED, CHECKED, INDETERMINATE, and confirmed by render batch 005 (R7). | hwp5 표 57 names the record only. | all 103 records |
| C8 | OWPML documents in the corpus use the namespace URIs `http://www.hancom.co.kr/hwpml/2011/*`; the standard uses `http://www.owpml.org/owpml/2024/*`. Local names agree, and the engine matches by local name. | owpml-ksx6101 §9.1, §10.1 | 260 documents |
| C9 | In every untouched click-here field holding text, that text (the guide text) has a character shape of its own, italic and red in every case, different from the field's; in every filled field the text has the field's character shape. | hwp5 표 33 p.24–25 (char shape: attribute bit 0 italic at byte 46, text colour at byte 52); how guide text is styled is not stated. | 18 untouched and 7 filled fields |
| C10 | The content of an untouched click-here field is its guide text. Besides the command form of the owpml-ksx6101 §10.7.3.1 sample, some documents use an older form `<guide>;<help>;…` (with `\;` for a semicolon), whose first part is the guide text. | owpml-ksx6101 §10.7.3.1–10.7.3.2 (guide text “Direction”, one command form) | 18 untouched fields |

Also observed and handled without being relied on: 5,503 paragraphs in 77
HWP 5.0 documents (and 325 OWPML paragraphs) have no line segments at all,
with a line segment count of 0 in the header (checked by
`tools/check/corpus.js`), so a paragraph without its layout cache occurs
in real files; line segments of one

tolerates.

## Open questions for the rendering corpus

Line segments and click-here fields are settled by batch 001 (R0–R4), and
the changes made for them are confirmed by batch 002: 90 of its 93
checkable expectations hold; the 3 that fail are a spacing cell without a
label whose empty paragraph is styled red (form 2156), which a render
batch fills but label matching never does. Still open:

* Blanks made of spaces inside a paragraph (“성명:　　　　”) and check boxes
  are filled; batch 004 checks that the text after a filled blank stays in
  place with the widths of R5, and that marking a check box changes nothing
  but the box.
* Form objects other than check boxes and radio buttons (combo boxes, edit
  boxes, …) are left untouched; the corpus has none. Check boxes and radio
  buttons (8 of the 2,464 HWP 5.0 documents, 103 controls; no OWPML
  document) are marked through C11 (R7).
* One verified fill (batch 004, A18: “본적:” then 37 underlined spaces in
  함초롬바탕, 0888.hwp) moved the text after it by 0.95 em, where the width
  model predicts 0.16 em; the spaces of that line print at about 0.45 em
  instead of 0.50. Not explained yet.
